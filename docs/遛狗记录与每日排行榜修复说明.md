# 留味儿：每日排行榜与轨迹恢复

本次已修改本地项目；云函数、索引和权限仍需在资源方云环境部署，尚未做真机联调。

## 1. 排行榜问题的定位

旧代码在 `pages/user/user.js` 中只查询 `todayDistance > 0`。字段名称虽然叫“今日里程”，但实际上只有用户再次结束遛狗时才会根据 `lastWalkDate` 覆盖。昨日走过、今日没有结束遛狗的用户，昨日里程会继续进入榜单。

旧结算还存在三个问题：

1. 日期由手机本地时区决定，无法统一北京时间。
2. 整段轨迹归到结束当天，跨午夜的遛狗会错误归属。
3. 先读档案再覆盖里程，重复提交、并发提交可能重复计数或覆盖彼此。

## 2. 排行榜的新数据模型

不在午夜清空用户资料。新增以下两个集合，客户端通过 `walkStats` 云函数查询和提交：

| 集合 | 一条记录的含义 | 关键字段 |
| --- | --- | --- |
| `pd_daily_stats` | 一位用户在一个北京时间自然日的统计 | `appid`, `owner`, `dayKey`, `distance`, `name`, `breed` |
| `pd_walk_sessions` | 一次遛狗最近已接受的累计快照 | `owner`, `revision`, `status`, `dailyDistances` |

当前项目一位用户一份宠物档案，因此按用户排名；如以后支持多宠物，应把已鉴权的 `petId` 加入会话和每日统计主键。

日期统一为北京时间 `00:00:00` 至次日 `00:00:00`，左闭右开。云函数决定榜单查询日期；客户端只负责采样时间戳和线段分日。跨午夜相邻采样的距离按两侧时间占比拆分，这属于对采样间路线的估计，不意味着能得到两次 GPS 采样之间的真实每一步。

客户端上传每个日期的累计米数和单调递增 `revision`，不直接增加某个全局字段。服务端事务中计算：

```js
const delta = incomingDailyDistance - previouslyAcceptedDailyDistance;
// 同一事务内更新每日累计与会话已接受版本。
```

相同版本重试、旧请求迟到都不会重复计数。结算后的会话不可再次增加。事务冲突由 SDK 事务机制处理，失败请求保留本地快照重试。事务机制参考：https://docs.cloudbase.net/database/transaction 。

榜单查询先按 `appid`、`dayKey` 和正距离筛选，再按距离降序取前十。同距离按文档 ID 稳定排序。仅返回展示字段，不返回 OPENID。

前台每30秒刷新，页面 `onShow` 立即刷新，午夜定时器先清掉昨日列表再查询；`onHide/onUnload` 清理页面定时器。隐藏前的旧请求不会覆盖新请求。后台定时器可能暂停，因此回到前台重新查询是必需的。午夜断网展示加载失败，不会把昨日榜当今日榜。

正在遛狗的统计随有效坐标最多约每15秒尝试同步，结束时强制同步；网络与定位频率会影响实时性。

## 3. 轨迹丢失的定位和修复

旧轨迹仅存在地图页的 `data.routePoints` 和 `walkPoints`，没有任何持久化；页面 `onUnload` 还会解绑监听、停止定位。页面重建或小程序被回收后，内存当然为空。仅在 `onHide/onUnload` 存档也不足够，系统可能没有给退出回调执行机会。

新增 `services/walk-recorder.js`，在 App 启动时创建唯一服务：

```js
// app.js
onLaunch() {
  this.walkRecorder = new WalkRecorder();
  // 原有云环境初始化见实际源文件。
},
onShow() { if (this.walkRecorder && this.cloud) this.walkRecorder.show(); },
onHide() { if (this.walkRecorder) this.walkRecorder.hide(); }
```

服务负责以下事项：

1. 开始时先保存会话，再调用 `wx.startLocationUpdateBackground({ type: 'gcj02' })`，只绑定一个位置监听。
2. 每收到有效坐标，更新累计距离、按日米数和递增版本，同步写本地存储。每200个点一片，避免整条路线塞进单个存储项。
3. 先写坐标分片，再写包含 `pointCount` 的元数据。恢复只读取元数据确认过的点数。
4. App 冷启动自动恢复；恢复后的首点带 `breakBefore`，不连接失联前后的两点。两次有效点相隔超过60秒也断线。
5. 过滤非法坐标、误差超过50米的点、短于3米的抖动和速度超过8米/秒的异常线段。阈值集中在服务文件，可根据真实采样调优。
6. 页面仅订阅服务状态；地图页卸载只取消 UI 订阅，不停止应用级定位。结束遛狗才停止定位。
7. 点击结束先持久化 `pending` 状态，再提交云端；失败显示“重试提交”。云端确认后才删除缓存。响应丢失后重试也不会重复计数。
8. 写入失败停止采集并提示，不把未持久化的点继续显示成已记录。释放存储空间后重新打开可恢复上次成功保存的进度。

地图显示累计米数；中断后显示说明并将轨迹画成多个独立线段，单点段不会传给地图 polyline。

必须明确的能力边界：后台定位要求微信接口开通和用户授权；系统杀死小程序或微信进程后，JS 和 GPS 回调均无法继续执行。本修复保证同一设备、存储未被清除时恢复已经保存的进度，无法补回回收期间没有采样的路径。实际路线保存在本地，云端保存按日统计快照；卸载、清理小程序数据、换设备不属于本地恢复范围。后台定位说明参考腾讯地图官方仓库：https://github.com/TencentLBS/tencentmap-miniprogram-skill/blob/main/references/wx_location_api/wx.startLocationUpdateBackground.md 。

## 4. 必须完成的云开发操作

1. **确认资源方环境。** 你的 `app.js` 使用 `new wx.cloud.Cloud({ resourceAppid, resourceEnv })` 跨账号环境对象。所有新集合、索引和 `walkStats` 必须在此资源方环境中建立。不要只上传到调用方默认环境。确认跨账号共享授权包含新函数；没有资源方权限时，需要资源方管理员执行本节。
2. **创建集合。** 在该环境的“数据库”中新建 `pd_daily_stats`、`pd_walk_sessions`。保留原有 `pd_users`，不要删除现有资料。
3. **设置安全规则。** 对两个新集合设置客户端不可读写，所有读写走鉴权云函数。自定义规则可使用：

   ```json
   { "read": false, "write": false }
   ```

   云函数以服务端权限执行。`pd_users` 继续使用现有资料/名片功能所需权限，并确保客户端只能修改自己的档案。
4. **建立索引。** 在 `pd_daily_stats` 添加组合索引：`appid` 升序、`dayKey` 升序、`distance` 降序、`_id` 升序，对应实际查询。等待索引建立完成；若控制台对默认 `_id` 索引有特殊处理，按查询报错提示建立等价索引。无需午夜定时清零函数。
5. **上传新云函数。** 开发者工具中右键 `cloudfunctions/walkStats` → “上传并部署：云端安装依赖”，选择资源方环境。已有依赖版本与项目其他函数一致，运行时使用平台支持的 Node.js 版本。确保该环境支持服务端数据库事务。
6. **验证身份。** 在真实小程序端调用 `getApp().getIdentity()`，检查返回 OPENID 是否对应自己的 `pd_users._openid`。本实现优先使用跨账号 `FROM_OPENID/FROM_APPID`，普通环境使用 `OPENID/APPID`。不要由前端传 OPENID 进行鉴权。如果旧资料的 `_openid` 命名空间不同，先核实历史环境和共享身份映射，不能将全表第一条资料当成自己。
7. **验证函数。** 真机建立自己的狗狗档案，开始遛狗后走一段有效距离。查看新集合是否生成当天记录，结束后会话状态是否为 `finished`。另一个账号应能看到榜单展示数据。
8. **旧里程处理。** 新榜单从新统计启用后累计；旧 `todayDistance/lastWalkDate` 不再参与结算，旧展示字段可以暂时保留。旧数据没有分日轨迹，无法可靠重建历史或拆分跨日路线。如果必须保留上线当天的旧里程，管理员应在切换前暂停旧版写入，以正确的来源 AppID/OPENID 生成相同每日主键，仅导入 `lastWalkDate` 等于当天且尚未计入新系统的数据；完成并核对后再启用新版。不要反复导入。简单方案是在北京时间零点切换，以新自然日开始统计。

## 5. 微信后台定位与隐私操作

项目 `app.json` 已包含后台定位配置，无需再重复添加：

```json
{
  "requiredPrivateInfos": ["getLocation", "startLocationUpdateBackground", "onLocationChange"],
  "requiredBackgroundModes": ["location"],
  "permission": {
    "scope.userLocation": { "desc": "用于地图与遛狗轨迹" },
    "scope.userLocationBackground": { "desc": "用于后台持续记录遛狗轨迹" }
  }
}
```

1. 小程序管理后台 → 开发/开发管理 → 接口设置，查看后台持续定位是否可申请并已开通。该能力存在类目、资质限制，配置代码不能替代开通。
2. 在用户隐私保护指引中准确声明地理位置及后台轨迹用途，按后台要求配置相关隐私接口。
3. 真机开启手机定位服务，并授权“使用小程序期间和离开小程序后”。此前拒绝授权的用户需要在小程序设置中修改。
4. 在真机测试切去聊天、锁屏、回到小程序。开发者工具不能替代系统后台定位行为验证；不同机型的后台采样频率可能不同。
5. 若类目不允许后台持续定位，当前录制会明确报错并保留会话；此时只能提供已获许可的前台记录能力和恢复提示，不能承诺后台连续轨迹。

本次没有新增步数传感器统计，“距离”是由 GPS 轨迹估算的米数。

## 6. 验证步骤

本地运行：`node --test tests/walk.test.js`。测试不依赖微信或云账号，服务端使用 SDK 替身，因此不能代替真实环境联调。

真机验收：

1. A用户昨天走1000米，今天无记录：A不应进入今日榜。B今天走500米，应只显示500米。
2. 在北京时间23:59开始，00:01结束：检查两天各自的里程；可在隔离测试环境缩短日期边界测试，不要改生产设备时钟来伪造记录。
3. 榜单页停留过午夜、后台过午夜后回来：都不能显示昨日榜。午夜断网显示失败，不伪装成今日数据。
4. 记录两段坐标后切去微信聊天、锁屏，再返回：原路线和累计距离保留，且监听不重复。
5. 记录后让进程结束，再重新打开：恢复旧轨迹，恢复后的点不与中断前直连，中断路段不计里程。
6. 结束时断网：显示“重试提交”；重新打开、恢复网络后再次提交，缓存才清理。
7. 模拟云端提交成功但响应丢失，再次提交同一版本：每日米数不能翻倍。并发会话应分别增量累加。
8. 拒绝后台定位、关闭手机定位、存储不足：给出明确提示，不能静默清空已保存记录。

服务器验证了身份、版本、日期范围和基本里程上限，但 GPS 与采样时间仍来自客户端；若排行榜涉及奖品或结算，应增加服务端轨迹校验及风控。当前每次遛狗最多跨31个统计日，正常应在当天结束遛狗。
